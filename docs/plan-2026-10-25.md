# Plan, 2026-10-25: mockups, bot fix, restructure, GitHub, then the real UI

The decisions in this plan are recorded one by one in [decisions/](decisions/README.md).

## Context

The project grew fast and got hard to read: placeholders next to real code, duplicate mockups and instruction files, no dependency pinning, and 671 MB of PNG logs. Wanted, in this order:
1. better mockups, with a hub that runs everything and later becomes **darbit Studio** (building bots from recorded macros plus image checks, without code);
2. the bot's fight bug fixed;
3. a standard, modular structure for both repos: a dev darbit and a released darbit kept apart, documentation everywhere, and AI-tool config done properly;
4. GitHub used properly;
5. then the real app.

**Decisions taken (2026-10-25):**
- **Disk and repos:** repos go in `C:\Users\FMehm\Projects`. The bot runs a tagged release of darbit. darbit becomes one monorepo (library, web UI, VS Code extension).
- **Tooling and packaging:** uv for Python. One `darbit` package, with an `app` extra for the hub, server and windows.
- **GitHub:** darbit goes public at v0.2.0; ad-bot stays private.
- **UI process:** one more HTML concept round, then real Svelte components in Storybook.
- **AI rules:** project rules live only in each repo (no global or dotfiles setup). Placeholders stay. The 3 s wait before attacking stays.

**Researched facts this plan relies on:**
- Claude Code reads a root `AGENTS.md` natively when the project has no `CLAUDE.md` or `CLAUDE.local.md`; it reads skills only from `.claude/skills/`.
- Antigravity reads `AGENTS.md` and `.agents/rules/`; Gemini CLI reads `.agents/skills/` before `.gemini/skills/`.
- Codex, Cursor and Copilot read `AGENTS.md`.
- Private repos on GitHub Free can't use rulesets or Pages (the API answered 403).

### C5. Code standards (written in `docs/style/code.md`; enforced by pre-commit and CI)
- **Layout:** src layout, `py.typed`, type hints everywhere. The public API is `darbit/__init__.py` only.
- **Checks:** `ruff check` and `ruff format`, with `D` rules (Google convention) on public modules; `pyright` in basic mode; `pytest`.
- **Docstrings:** one line, plus args only when not obvious. Comments only say why. `docs/reference` is generated from the docstrings.
- **Docs:** Keep-a-Changelog. An ADR for each decision. Every PR updates the changelog and the docs it touches.

### C5b. Plain, readable Python (written in `docs/style/code.md`; applied to ad-bot first, then darbit)
The code was hard to follow: partly missing docs, partly syntax many Python users never meet. Rules:

- **Banned in ad-bot**, and avoided in darbit unless it's clearly simpler:
  - `:=` (walrus);
  - `lambda` (except a one-word key);
  - nested or conditional comprehensions, and `dict.fromkeys` tricks;
  - `getattr` dispatch, `@staticmethod` without need, chained ternaries;
  - `from __future__ import annotations`, and complex type hints (`tuple[Match | None, bool]` becomes a small named result, or two simple returns).
- **Use instead:** plain `for`/`if`, early `return`, small functions with verb names, simple dataclasses for results, constants with comments, one idea per line.
- **Every module** starts with a 2–4 line plain-English summary of what it is for. Every bot screen or mode has a short "how this works" in ad-bot `docs/code-map.md`.
- **The darbit public API** (what bots call) stays SikuliX-simple; the readable-code rules apply first to everything a bot author sees: `examples/`, docs and the bot.
- **A simplify pass on ad-bot** (B2, right after the bug fix):
  - rewrite `speed_raid_list.py`, `fight.py`, the modes and the screens in this style, behaviour unchanged, with tests guarding it;
  - add `docs/code-map.md`.

  Then the same pass on darbit's `runtime/` and `capture/`.

## E. The hub becomes darbit Studio (vision, planned now so nothing blocks it)

Bots can be built in the Studio without code, and code is never locked out:

1. **Record with checks as you go.** While recording, pause (`Ctrl+Alt+P`, or the bar's button), then **Add check**:
   - an image check opens the capture tool on the frozen screen, saves the picture into the bot's `assets/images/`, and inserts a step at that exact point (wait for it, if seen / if not seen, until gone);
   - other checks: a colour at a point, a region changing, and text later (T24).

   Resume, and the recording carries on after the check. A recording is a flow from the start, with its checks in place.
2. **Edit the flow**, as a list or a graph: timings, branches, loops, retries, variables, named actions.
3. **Code wherever the editor stops.** A **Code step** calls a Python function from the bot (`call: ad_bot.tactics.dodge`) or holds a short inline script. Bot authors can add their own steps to the editor with `@d.action`: typed parameters become a form in the Studio's step palette, so custom behaviour looks like a built-in step.
4. **Run and test** step by step in the run panel, with breakpoints.
5. **Two-way with code:**
   - **Flow → Python:** export writes readable darbit code, one statement per step.
   - **Python → flow:** no decompiler needed. Flows are saved as "flow-shaped" Python: a `@d.flow` function using only flow statements (`d.wait`, `if d.exists(...)`, `for`/`while`, `d.press`, calls). The Studio reads it back with Python's own `ast` parser. Anything outside that shape shows as a Code step, kept verbatim and editable as text.

   So the same file opens in the Studio and in VS Code, and edits in either survive.

6. **Functions are actions.** A flow can define functions: a named sub-flow with inputs (for example `pick_character(name)`) and an optional result (`found`, `match`). Functions:
   - show in the step palette next to built-in steps and `@d.action` Python steps, and are called the same way;
   - can be shared between flows, and between bots as a library;
   - export to Python as a `def`, and a `def` in a `@d.flow` file reads back as a function.

   Built-in steps, flow functions and Python actions are one concept in the editor: an **action** with parameters.

What this changes now:
- **The format:** one flow model and schema for the recorder, the player, the editor and export (T14 is redefined). It includes functions (`define`, `call`, `return`) from the start. Steps: input steps, checks (`wait_for`, `if`/`else`, `until`, `retry`, `on_fail`), `repeat`, `set`, `call`/`code`, plus named actions.
- **New tasks:**
  - **T26 "Checks while recording"** (part of T15);
  - **T27 "Flow editor"** (after T16);
  - **T28 "Flow ↔ Python"** (export, and reading `@d.flow` back with `ast`);
  - **T29 "Custom steps with `@d.action`"**.

  Roadmap: v0.4 becomes "runs and flows", and the editor and round trip go into v0.5 with the Studio.
- **The GUI comes first:** the concept round in A designs these screens before any engine work, so the end result can be seen early:
  - the recorder paused, with its Add check panel;
  - the flow editor, with a Code step and a custom step;
  - the export view, with flow and Python side by side.
- **Naming:** "hub" becomes **Studio** in the docs, mockups and task pages. The concept round in A adds a Flow editor screen: a steps list with an inline target picker (from the library or captured on the spot), an inline condition builder, and run/step controls.
- **An ADR** records "Studio + library from one package (`darbit[app]`)", so a standalone Studio installer later (T25) is a packaging step, not a rewrite.
